Level 3 — Prompt Engineering

Debugging & Iterating Prompts When They Almost Work

Learning objective: Debug an "almost-working" prompt systematically by diagnosing its root failure category, changing one variable at a time, and running a mini test suite to catch regressions.

Definition

Systematic prompt debugging replaces guesswork and random rewording with a repeatable three-step engineering loop: (1) diagnose the root failure category, (2) isolate one targeted edit, and (3) test against a 4–6 case check (normal + edge inputs) so fixing one bug never silently breaks yesterday's working cases.

How It Works (The 4 Failure Categories & Triage Loop)

When an output is 80% right and 20% wrong, stop tweaking random adjectives. Almost every prompt bug maps to one of four root causes:

Failure Category Symptom in Output Targeted Fix
1. Missing Context Model invents defaults, guesses missing figures, or misses internal policy Supply the missing rule/reference or add an explicit null / "unknown" escape hatch
2. Ambiguous Instruction Vague words ("short", "urgent", "main total") cause inconsistent choices Replace adjectives with concrete rules or 1–2 boundary few-shot examples
3. Loose Output Contract Facts are right, but extra intro text or markdown fences break JSON parsing Specify exact schema, field types, and "Return ONLY raw JSON; no markdown fences"
4. Task Too Big for One Step Model drops middle instructions when extracting, judging, and formatting at once Split into a 2–3 step prompt chain instead of stuffing more rules into one call
  1. Diagnose before editing: Tag each failing example with one of the 4 buckets above.
  2. Isolate one change at a time: Editing five lines at once hides which edit fixed the bug—and which caused a side effect.
  3. Regression-check 4–6 cases: Keep 2–3 standard "happy path" inputs alongside 2–3 tricky edge cases and re-run all of them after each change.

Worked Example: Avoiding "Whack-a-Mole" Invoice Regressions

An invoice extractor passes standard SaaS bills, then hallucinates $52.50 when a courier quote says Final Total: TBD.

  • Reactive Quick Hack: Adding "Only read lines literally labeled Final Total; otherwise output null" fixes the courier quote—but immediately breaks normal invoices labeled Grand Total: $432.00!
  • Targeted Root-Cause Fix: Diagnose as Missing Escape Hatch + Ambiguous Field Rule: keep Grand Total / Amount Paid precedence clear, and add "Never average estimates; if final payment is TBD or missing, return null." All normal and edge cases pass together.

Common Pitfall: Whack-a-Mole Patching & All-Caps Shouting

Writing narrow, reactive patches for today's bug—without re-running yesterday's passing examples—creates prompt regressions where fixing Case 3 silently breaks Case 1. Just as ineffective is shouting in uppercase ("CRITICAL!! NEVER MAKE MISTAKES!!"): louder wording adds noise without fixing missing context, ambiguous criteria, or loose schemas.
