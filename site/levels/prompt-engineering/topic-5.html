Level 3 — Prompt Engineering

Show, Don't Just Tell: Using Examples (Few-Shot Prompting)

Learning objective: Use 2–4 well-chosen Input → Output examples (few-shot prompting) to lock in format, tone, and subtle edge-case boundaries—without creating label bias.

Definition

Zero-shot prompting asks a model to complete a task using instructions alone. Few-shot prompting includes 2–5 concrete Input → Output demonstrations directly in the prompt so the model infers your exact schema, tone, granularity, and boundary rules by pattern matching.

How It Works (Why Examples Beat Paragraphs of Rules)

Prose adjectives like "concise, calm, non-defensive" or "strict JSON" still leave dozens of valid interpretations. Because language models predict text by continuing patterns in context, a handful of real Input → Output pairs simultaneously settles punctuation, JSON key names, sentence length, and judgment calls that would take three paragraphs to explain.

Approach What You Include Best For Common Watch-Out
Zero-Shot Task + rules only (0 examples) Simple summaries, brainstorming, open Q&A Drifts on strict formats, custom tone, or subtle categories
One-Shot 1 clean example Teaching an output template quickly May over-copy that single example's wording or label
Few-Shot (2–4) 2–4 diverse examples + edge cases Classification, extraction, consistent brand tone Unbalanced labels skew predictions toward the majority

Three rules for choosing high-leverage examples:

  • Stay compact (2–4 pairs): Two pairs lock the output shape; adding 1–2 tricky edge cases sets the decision line without bloating tokens.
  • Demonstrate the hard boundaries: Easy inputs only teach syntax. Include borderline examples (e.g., an angry customer requesting a feature, or an unclear note mapped to unknown) where rules alone wobble.
  • Balance labels and styles: Cover different output labels and tones evenly so the model doesn't treat one label as the automatic default.

Worked Example: Resolving Ticket Ambiguity with 3 Examples

Suppose your zero-shot prompt says: "Classify tickets into billing, bug, or feature, and set priority." Angry customers requesting missing features often get misfiled as high-priority bugs. Adding three balanced examples fixes both schema and nuance: 

Input: "Can I get last month's PDF receipt?"
Output: {"category": "billing", "priority": "normal"}

Input: "Love manually exporting 12 CSVs every Friday lol—bulk export please."
Output: {"category": "feature", "priority": "normal"}

Input: "It's broken on my screen, please fix."
Output: {"category": "unknown", "priority": "unknown"}

Example 2 proves sarcasm is still a feature (not a bug), while Example 3 gives a clean escape hatch instead of guessing.

Common Pitfall: Label-Imbalance & Copycat Bias

Few-shot examples teach label frequency as well as format. If all 3 examples happen to be billing / high (or start with "We sincerely apologize for the inconvenience"), the model infers that pattern as the norm and over-predicts billing / high—or repeats your corporate boilerplate—on completely unrelated inputs. Always audit your example pool for accidental skew.
