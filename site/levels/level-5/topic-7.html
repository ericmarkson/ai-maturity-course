Level 5 — Intermediate+

Basic Model Deployment and Serving

Learning objective: Choose between batch and real-time serving for a workload, trace the API request-to-inference path, and quantify how request batching trades individual latency for total throughput.

Definition

Model serving exposes a trained model artifact so applications can turn live inputs into predictions reliably. Rather than embedding heavy model code inside every client app, teams wrap the model and its preprocessing behind a versioned network API endpoint (or scheduled batch pipeline) engineered around strict latency, throughput, and availability targets.

How It Works

1. Behind an Inference API: A client sends JSON (e.g., POST /predict) to a serving gateway, which validates the schema, applies exact feature preprocessing, runs a forward pass on CPU/GPU, and returns the prediction alongside model_version and confidence metadata.

2. Batch vs. Real-Time/Online Serving: Batch inference runs offline on a schedule (e.g., overnight churn scores across 2M accounts), maximizing hardware utilization at lowest cost per prediction. Real-time inference responds within milliseconds per user event (fraud checks, search ranking, chat).

3. Dynamic Batching (Latency vs. Throughput): Because GPUs parallelize matrix multiplications, scoring 8 queued inputs together takes only slightly longer than scoring 1—boosting throughput (requests/second). However, early arrivals wait in a queue until the batch fills or a timeout fires, increasing tail latency (ms per request).

4. Versioning & Safe Rollouts: Tagging every prediction with model_version lets teams run canary traffic splits (e.g., 5% on v4, 95% on v3) and instantly roll back if latency spikes or error rates climb.

Worked Example: Quantifying the Batching Trade-Off

Suppose a GPU sentiment endpoint takes 40 ms to score 1 text, or 60 ms to score a batch of 8 texts together:

  • Real-time (batch = 1): First-request latency is 40 ms, but max single-worker throughput is capped at 1000 / 40 = 25 req/s.
  • Micro-batching (batch = 8, arriving every 10 ms): Request #1 waits 70 ms for #8 to arrive plus 60 ms compute (130 ms latency), yet all 8 finish together—raising throughput to 8 / 0.060 ≈ 133 req/s (over 5× higher capacity).

Common Pitfall: Training–Serving Skew

A model deployed behind a clean API will still fail silently if the serving server preprocesses inputs differently from the training notebook—for instance, using different tokenizer rules, missing-value defaults, or stale feature scaling statistics. Always serialize preprocessing transforms alongside model weights and validate identical outputs on golden test payloads before shipping.
