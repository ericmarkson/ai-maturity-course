Production ML Systems at Scale

Learning objective: Define latency, throughput, and error-budget SLOs for production ML serving, select GPU-aware autoscaling and rollout strategies (shadow, canary, A/B) for a given risk profile, and design circuit breakers and fallback tiers to prevent cascading outages.

Definition

Production ML systems at scale encompass the serving architecture, telemetry, rollout discipline, and fault tolerance required to run models under real traffic SLOs. Offline benchmark accuracy means little if tail latency violates product expectations, GPU cost per 1,000 requests breaks unit economics, or a subtle regression breaks live users before monitoring catches it.

How It Works

Scaling ML inference requires managing four coupled operational dimensions:

  • SLIs, SLOs & GPU utilization: Track tail latency (p95/p99 Time-To-First-Token and total latency), throughput (tokens/s or req/s), and error rate against explicit Service Level Objectives. Dynamic batching increases GPU Tensor Core utilization and drops cost per request, while queueing wait adds tail latency; streaming tokens lowers perceived user wait even when full generation takes seconds.
  • ML-aware autoscaling: Traditional CPU utilization triggers fail for GPU-bound models. Autoscale on GPU KV-cache occupancy, active request queue depth, or tokens/sec saturation, and mitigate 20–90s weight-loading cold starts with pre-warmed pools or cached fast storage.
  • Risk-tiered rollouts: Shadow deployment mirrors live requests asynchronously to the candidate model without exposing users (ideal for verifying crashes, memory, and p99 latency at 2× compute cost). Canary releases shift a small traffic slice (e.g. 1–10%) to catch regressions early, while A/B tests split traffic across large enough samples to measure product-level lift.
  • Graceful degradation: Timeouts, rate limits (token-bucket per tenant), and circuit breakers isolate failing model pods so retries do not snowball into cascading outages — shedding load cleanly to a smaller, cheaper fallback model when queues saturate.

Worked Example

Suppose a customer-facing assistant has a p99 latency SLO ≤ 1,200 ms and baseline error rate of 2.0%. You want to ship a new quantized checkpoint that might have a hidden long-context regression pushing errors to 5.5%.

First, run a shadow deploy for 30 minutes to verify zero OOMs and confirm p99 latency stays under 1,200 ms. Next, launch a 10% canary. At 100 requests total (10 canary), observing 1 error looks like 10% — pure binomial noise. After sending 10,000 total requests (~1,000 canary), the canary shows ~55 errors (5.5%, 95% CI [4.1%, 7.0%]) vs. control ~180/9,000 (2.0%, 95% CI [1.7%, 2.3%]). Because the gap is statistically clear, automated rollback halts promotion before 90% of users are impacted.

Common Pitfall

Scaling on CPU metrics & reacting to tiny canary samples: Inference servers often sit at 15% host CPU while GPU compute or KV-cache queues hit 100%, causing CPU-based Kubernetes HPAs to scale too late. Just as common, teams either monitor only p50 latency (missing batching queue spikes that wreck p99) or abort/promote a canary after 30 requests when sampling noise dominates the signal.
