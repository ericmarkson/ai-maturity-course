Mixture-of-Experts Architectures

Learning objective: Explain how sparse top-k MoE routing decouples total model capacity from per-token FLOPs, formulate the load-balancing problem and auxiliary loss, and analyze MoE VRAM footprint, All-to-All communication overhead, and batch-size tradeoffs in production.

Definition

Mixture-of-Experts (MoE) is a sparse neural architecture that replaces each dense Transformer feed-forward network (FFN) with N parallel expert FFNs and a lightweight router (gating network). For every token, the router activates only the top k experts (typically k = 1 or 2 out of 8–256), scaling total parameter knowledge while keeping per-token arithmetic FLOPs proportional only to active parameters.

How It Works

Self-attention layers, embeddings, and layer norms remain shared across all tokens, while each FFN block becomes a gated bank of experts {E1, …, EN}. For hidden state x, a linear router computes logits h(x) = Wgx, keeps the top k scores, applies Softmax to obtain routing weights gi, and outputs the weighted sum Σ g_i(x) E_i(x) over those k chosen experts.

  • Routing collapse & load balancing: Without balancing, gradient descent hits a "rich-get-richer" loop where a few experts receive most tokens while others starve and stay untrained. Training adds a differentiable auxiliary load-balancing loss L_aux = α · N · Σ f_i · P_i (penalizing correlation between fraction of tokens routed fi and router probability mass Pi), or uses auxiliary-loss-free dynamic router bias updates (DeepSeek-V3 style).
  • Expert parallelism & All-to-All overhead: When experts are sharded across GPUs, tokens must be dispatched via All-to-All collective communication and combined back. Hardware buffers enforce a capacity factor; overloaded experts either drop excess tokens or stall peers waiting for the straggler GPU.

Worked Example

Take a Mixtral-style 8×7B sparse MoE: shared attention and embeddings account for ~1.9B parameters, and each layer holds 8 FFN experts (~5.6B per full expert stack), giving 1.9B + 8 × 5.6B = 46.7B total parameters. With top-2 routing, each token executes only shared layers plus 2 experts: 

Active params/token = 1.9B + 2 * 5.6B = 13.1B  (~28% of total weights)

Per-token FLOPs resemble a ~13B dense model while capacity rivals a ~45B dense model. However, all 46.7B weights must sit in GPU HBM (~93 GB in BF16, ~47 GB in FP8), because successive tokens in a sequence can route to any of the 8 experts.

Common Pitfall

Assuming MoE slashes VRAM or accelerates batch=1 inference linearly: MoE reduces compute FLOPs per token, not memory footprint — you still pay VRAM for every expert. Moreover, at small serving batch sizes (B = 1–4), autoregressive decode is memory-bandwidth bound, and across 32+ layers nearly every expert may be touched over a short burst, while distributed All-to-All latency adds overhead unless batch size is large enough to amortize expert weight loads.
