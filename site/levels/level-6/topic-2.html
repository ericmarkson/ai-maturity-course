Structured Outputs, Constrained Decoding & Tool Protocols (MCP)

Learning objective: Learner can explain how grammar-based logit masking guarantees JSON Schema compliance during decoding, apply strict schema rules (required, enum, additionalProperties: false), and trace a Model Context Protocol (MCP) tools/call exchange while distinguishing syntactic compliance from semantic correctness.

Definition

Structured outputs guarantee that an LLM emits data conforming to a machine-readable schema (typically JSON Schema) rather than unpredictable prose. Constrained decoding enforces that guarantee at inference time by masking illegal next tokens before sampling, while the Model Context Protocol (MCP) standardizes how AI applications discover and invoke external tools, data resources, and prompt templates over JSON-RPC 2.0.

How It Works

Standard autoregressive generation picks the next token from the model's entire vocabulary V via softmax(z / T). Even with temperature = 0 and instructions like "output raw JSON only," an unconstrained model often emits markdown fences (```json), conversational preambles, missing commas, or unrequested keys because those sequences carry high prior probability in pretraining data.

  • Regex & CFG logit masking: Before decoding starts, the inference engine compiles a regex or JSON Schema into a deterministic finite automaton (DFA) or context-free grammar (CFG). At every generation step, the engine queries the active parser state to find the subset of vocabulary tokens that keep the prefix valid, sets all other token logits to −∞ (probability 0), and samples only from the legal remainder.
  • Strict schema discipline: Production structured-output modes require every object schema to declare explicit type, required fields, constrained enums or patterns, and additionalProperties: false. Without additionalProperties: false, the grammar permits arbitrary extra keys—letting the model invent fields downstream code never reads.
  • MCP client-server architecture: Rather than writing custom glue code for every LLM host and external service, an MCP Host (e.g., an IDE or agent runtime) runs MCP Clients that connect over stdio or HTTP/SSE using JSON-RPC 2.0 to MCP Servers. Each server exposes three primitives: Tools (model-controlled executable actions with a JSON Schema inputSchema), Resources (application- or user-selected read-only context such as db://schema), and Prompts (user-triggered workflow templates).

Worked Example

Suppose tool search_orders enforces required: ["customer_id", "status"], status enum ["open", "shipped", "refunded", "all"], and additionalProperties: false. After generating the prefix {"customer_id": "cust_104", "status": ", the CFG parser allows only tokens spelling open", shipped", refunded", or all"; tokens like pending" or } receive −∞ logits. Once valid arguments are decoded, the MCP client sends a JSON-RPC request and receives a typed server result: 

// Client -> MCP Server (tools/call)
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "search_orders",
            "arguments": {"customer_id": "cust_104", "status": "open", "limit": 5}}}

// MCP Server -> Client (tool result)
{"jsonrpc": "2.0", "id": 7,
 "result": {"content": [{"type": "text", "text": "[{\"order_id\":\"ord_4821\",\"total\":89.50}]"}],
            "isError": false}}

Common Pitfall

Valid syntax is not semantic accuracy. Constrained decoding guarantees that customer_id is a well-formed string and status is in the enum, not that cust_999 exists in production or matches the user's intent. Worse, rigid schemas without an escape hatch (such as an "unknown" enum option or nullable field) can pressure a model into fabricating plausible-looking IDs or SQL queries just to satisfy the grammar—so MCP servers must still run semantic validation, authorization checks, and safe error reporting (isError: true).
