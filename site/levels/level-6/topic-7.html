Distributed Training Basics

Learning objective: Learner can distinguish data parallelism from model parallelism using a diagram and explain, in one sentence, why communication between devices becomes the bottleneck as you add more of them.

Definition

Distributed training splits the work of training a large model across multiple machines or GPUs so that models and datasets too large for one device can still be trained in a reasonable amount of time. Splitting the work also means the devices must periodically communicate — sync gradients, or pass activations between each other — and that communication is what eventually limits how much speedup you get from adding more devices.

How It Works

  • Data Parallelism (DP / DDP): Each of N GPUs holds a complete copy of the model weights and optimizer states, while processing a distinct shard of the training batch. After backpropagation, GPUs execute an All-Reduce collective to average gradients across devices before updating weights identically. DP scales cleanly until a single GPU can no longer hold the model + optimizer state.
  • Model Parallelism (Pipeline & Tensor Parallelism): When a model exceeds one GPU's VRAM, it must be partitioned across devices. Pipeline Parallelism (PP) assigns groups of sequential layers to different GPUs and passes activations forward/backward (mitigating idle "pipeline bubbles" via micro-batching). Tensor Parallelism (TP) splits individual weight matrices across GPUs in the same node, requiring ultra-fast All-Reduce syncs inside every layer.
  • Why Communication Limits Scaling: Adding GPUs cuts per-device compute work, but collective synchronization (gradient All-Reduce in DP, or inter-layer activation/tensor syncs in MP) grows with device count and network hops. Once sync time rivals compute time, throughput gains flatten sub-linearly.

Worked Example

Compare configurations on 4 × 80 GB GPUs:

  • Fits on one GPU (28 GB base + activations): Data Parallelism keeps a full replica on each GPU (~29.6 GB at batch 32), delivering near-4× speedup with ~11% All-Reduce gradient sync overhead.
  • Oversized model (120 GB weights + optimizer): Data Parallelism hits out-of-memory (OOM) immediately because 120 GB > 80 GB. Switching to 4-way Model Parallelism shards model state to ~30 GB per GPU, fitting inside 80 GB while accepting higher inter-device activation transfer overhead.

Common Pitfall

Ignoring interconnect topology and global batch-size drift. Running Tensor Parallelism across slow inter-node Ethernet instead of high-bandwidth intra-node NVLink stalls every transformer layer on All-Reduce latency. Similarly, scaling Data Parallelism from 2 to 16 GPUs without adjusting gradient accumulation or learning rate multiplies the global batch size by 8×, often destabilizing convergence.
