Intro to Evals for ML/LLM Systems

Learning objective: Learner can design a minimal eval set (5-10 test cases with expected criteria) for a simple task (e.g., a summarization prompt) and explain what "regression" means in an eval context.

Definition

Evals are systematic tests that measure how well an ML or LLM system performs on tasks that matter, going beyond a single accuracy number to catch failure modes before real users do. Instead of eyeballing a few outputs, you run the system against a fixed set of test cases and score each one against explicit criteria — so you can compare runs objectively, and re-run the same suite after any change.

How It Works

  • Three Grading Tiers: (1) Deterministic checks validate syntax, JSON Schema, regex patterns, or unit tests with zero ambiguity; (2) Reference-based metrics (exact match, ROUGE, semantic similarity) compare outputs against a gold answer when one exists; (3) Rubric / LLM-as-Judge grading evaluates open-ended quality along explicit criteria (groundedness, tone, completeness, brevity).
  • Handling Non-Determinism (pass@k vs. pass^k): When sampling with temperature > 0, a single pass/fail run can mislead. Teams track pass@k (probability that at least 1 of k independent attempts passes—useful for coding agents with verifiers) alongside pass^k (probability that all k trials pass—critical for customer-facing consistency).
  • Baseline Pinning & Regression Gating: Saving a versioned eval score as a baseline turns your eval suite into an automated CI gate: any prompt edit, model swap, or RAG chunk tweak that lowers the pass rate triggers a regression alert before users see it.

Worked Example

Suppose a 6-case product-review summarization suite enforces four rubric checks per output: product name, sentiment, star rating, and single sentence.

  • Prompt v1 (baseline): "Summarize this product review including product name, sentiment, and star rating in one sentence." → Passes 6/6 cases (100% baseline).
  • Prompt v2 (edited): Someone adds "Explain in detail" to sound richer. Outputs grow to multiple sentences, failing the single sentence check across all 6 cases (0%) — a clear caught regression relative to the 100% baseline.

Common Pitfall

Happy-path bias and test-set leakage into few-shot prompts. Building an eval suite exclusively from clean, short examples hides real failure modes (mixed sentiment, negation, missing metadata, adversarial formatting). Even worse, copying failing eval examples directly into your prompt's few-shot section causes the model to memorize the benchmark while generalizing poorly to unseen traffic—always split held-out regression cases from prompt development examples.
